저장소에 남아 있는 예전 실행 명령을 보면, 같은 옵션이 들어갔다가 빠지고 숫자가 줄었다가 다시 커진다. 동시 처리 시퀀스를 12개에서 6개로 줄였고, 며칠 뒤에는 3개까지 낮췄다. TP로 실행하다 DP를 써 보기도 했고, 지금은 다시 TP 8을 사용한다.

최종 명령만 보면 이런 과정은 보이지 않는다. 모델 경로를 지정하고 옵션 몇 줄을 붙여 실행한 것처럼 보인다. 실제로는 컨테이너가 계속 종료되는 문제를 먼저 다뤄야 했고, 실행이 안정된 뒤에도 기다리는 시간이 길거나 같은 요청의 속도가 달라지는 문제를 봐야 했다.

[이전 글](https://noahwannagohome.github.io/tech-b-log/posts/closed-network-llm/)에서는 내부 모델을 Claude Code와 Cline에 연결하기 위해 만든 게이트웨이를 다뤘다. 이번에는 그 뒤에서 모델을 실행하는 쪽의 이야기다. H200 8장으로 사내 코딩 에이전트를 운영하면서 어떤 설정을 바꿨고, 왜 다시 바꾸게 됐는지 정리했다.

## 먼저 컨테이너가 계속 살아 있어야 했다

초기부터 지금의 GLM-5.3-Flash를 쓴 것은 아니다. 6월 기록에는 GLM-5.1-FP8이 남아 있고, 7월에는 GLM-5.2로 교체했다. 모델과 vLLM이 바뀌는 동안 실행 옵션도 함께 달라졌다.

6월 17일 기록에는 “장문 컨텍스트 및 동시 요청 증가 시 프로세스가 불안정해지는 문제”라고 적혀 있다. 당시에는 동시 처리 수를 올리는 것보다 요청이 겹쳤을 때 프로세스가 유지되는지부터 확인해야 했다.

| 시점 | 바꾼 것 | 당시 확인하려던 문제 |
| --- | --- | --- |
| 6월 16일 | 동시 처리 시퀀스 12, MTP 3 | 초기 실행 구성 |
| 6월 17일 오전 | 시퀀스 12 → 6, 배치 토큰 상한 8192 추가 | 긴 입력과 동시 요청에서의 불안정 |
| 6월 17일 오후 | custom all-reduce 비활성화 | 반복 종료에 GPU 통신 구현이 관련됐는지 확인 |
| 6월 23일 | 시퀀스 3, RPC timeout·NCCL 로그 설정 | 제한을 더 낮추고 종료 문제 추적 |
| 7월 2일 | 드라이버·Fabric Manager·vLLM 환경 정비 | 버전 변경에 따른 실행·통신 문제 |
| 7월 8일 | GLM-5.2, 컨텍스트 204800, 시퀀스 4 | 모델 교체 후 장문 요청 운영 |

이 표는 당시 시도한 순서다. 예를 들어 custom all-reduce를 껐다는 기록은 그 구현을 원인으로 의심했다는 뜻이지, 종료 원인을 확정했다는 뜻은 아니다.

동시 처리 수를 줄이는 것도 성능을 개선한 결과는 아니었다. 한 번에 받아들이는 일을 줄여서 상태를 살피는 조치였다. 이후 설정이 다시 커졌다는 것까지 같이 봐야 당시 선택을 이해할 수 있다.

### 드라이버를 바꾼 뒤에는 다른 곳에서 막혔다

7월에는 NVIDIA 드라이버와 vLLM을 올리는 과정에서 Fabric Manager 버전이 맞지 않아 NVLink 통신에 문제가 생겼다. Fabric Manager를 드라이버에 맞춰 업데이트하고 해결했다.

여러 GPU를 함께 쓰는 환경에서는 모델과 추론 엔진만 맞춘다고 끝나지 않았다. 드라이버를 바꾸면 GPU 사이 연결을 관리하는 구성요소도 같이 확인해야 했다. GPU 한 장에서 돌아가는 예제를 따라 실행하는 것과는 확인할 범위가 달랐다.

이런 문제를 겪고 나면 실행 명령을 남기는 이유도 달라진다. 다음에 복사하려고 남기는 것에 더해, 어떤 환경에서 어디까지 동작했는지 구분할 기록이 된다.

## 코딩 에이전트의 부하는 사람 수로 설명하기 어려웠다

지금은 하루에 약 40명이 사용한다. 이 숫자만 들으면 부하가 크지 않아 보일 수도 있다. 그런데 코딩 에이전트에서는 사람 한 명이 질문 하나를 보내고 끝내는 경우만 있는 게 아니다.

파일을 읽고, 수정하고, 명령을 실행한 뒤 결과를 다시 모델로 보낸다. 사용자는 한 번 지시했지만 모델 호출은 계속 이어진다. 다음 호출에는 앞에서 읽은 코드와 도구 실행 결과가 붙는다. 병렬 작업을 돌리면 한 사용자의 요청도 여러 개가 겹친다.

그래서 하루 사용자 수와 동시에 추론 중인 요청 수를 구분해야 했다. 요청 수가 같아도 입력이 몇천 토큰인지, 수만 토큰인지에 따라 서버가 하는 일이 달라졌다.

기존 운영 집계에서도 요청당 평균 입력은 6월의 5,008토큰에서 11월 집계의 93,393토큰으로 커졌다. 두 기간에는 모델과 사용자 작업도 바뀌었으므로 같은 부하의 전후 비교는 아니다. 다만 서비스를 운영하면서 감당해야 하는 입력 자체가 얼마나 달라졌는지는 보여준다.

긴 입력을 허용하려는 이유도 여기에 있었다. 코드와 실행 결과를 매번 잘라서 보내게 하면 에이전트가 작업을 이어가는 데 제약이 생긴다. 현재는 최대 컨텍스트를 1,048,576토큰으로 설정했다. 물론 이 상한을 지원한다는 것과 모든 사용자가 동시에 그 길이를 채워도 빠르게 처리된다는 것은 별개의 문제다.

## 생성 속도보다 먼저 보인 것은 첫 응답의 들쭉날쭉함이었다

모델 속도를 볼 때는 초당 몇 토큰을 생성하는지부터 보게 된다. 그런데 실제로 사용하면 답변이 시작되기 전의 기다림도 크게 느껴진다.

LLM은 입력을 먼저 처리하는 prefill과 이후 토큰을 생성하는 decode를 거친다. 긴 코드를 보냈다면 생성이 빠르더라도 입력 처리에서 오래 기다릴 수 있다. 여기에 요청 대기와 전달 경로의 지연도 더해진다.

당시 약 4만 토큰의 입력으로 반복 요청을 보냈을 때 다음과 같은 값이 나왔다. 출력은 300토큰이었다.

| 요청 | 첫 토큰까지 걸린 시간 | 출력 생성 속도 |
| --- | ---: | ---: |
| 1 | 3.06초 | 82.8 tok/s |
| 2 | 0.73초 | 79.0 tok/s |
| 3 | 3.04초 | 137.6 tok/s |
| 4 | 3.32초 | 59.1 tok/s |

두 번째는 빨랐다. 그런데 세 번째부터 다시 3초대로 돌아갔다. 출력 생성 속도가 가장 높았던 세 번째도 첫 토큰은 빨리 나오지 않았다.

이 값만으로 원인을 확정할 수는 없었다. 대신 생성 속도와 첫 토큰 지연을 따로 봐야 한다는 점은 분명했다. 당시 진단에서는 엔진 사이의 입력 토큰 부하 차이와 일부 요청에서만 나타나는 캐시 적중도 함께 확인됐다.

KV 캐시 점유율도 확인했다. 당시 관찰에서는 50% 미만이어서, 메모리가 꽉 찬 것만으로 지연을 설명하기 어려웠다. 그다음에는 요청이 어느 엔진으로 가는지, 앞에서 계산한 입력을 다음 요청이 다시 쓸 수 있는지를 살펴봤다.

## DP 8을 써 보니 캐시가 어디에 있는지도 중요해졌다

10월 22일 서빙 기록에는 기존 TP 8에서 DP 8과 EP를 사용하는 구성으로 바꾼 내용이 남아 있다.

TP는 한 요청 배치의 계산을 여러 GPU가 나누는 방식이다. DP는 여러 엔진에 요청 배치를 나눠 보낸다. 여러 사용자가 동시에 요청하는 서비스라면 DP도 비교해 볼 만한 구성이었다.

여기서 GLM 같은 MoE 모델은 한 가지를 더 구분해야 한다. DP 8과 EP를 함께 쓰면 모델 전체를 GPU마다 복제하는 것이 아니다. TP 1인 경우 Attention 가중치는 각 DP 엔진에 복제하고, Expert 가중치는 전체 EP 그룹에 분산한다.

하지만 요청을 분산하는 것과 캐시를 재사용하는 것은 함께 생각해야 했다. DP 엔진마다 KV 캐시가 따로 있기 때문이다.

![같은 prefix를 가진 후속 요청도 캐시가 있는 엔진으로 배정됐는지에 따라 재사용 여부가 달라지는 흐름](/tech-b-log/images/llm-dp-cache-routing.svg)

첫 요청을 엔진 A가 처리했는데 다음 요청이 B로 가면, A에 남은 계산 결과를 B가 자동으로 가져다 쓰지는 않는다. 각 엔진을 골고루 쓰는 것과 반복 입력을 덜 계산하는 것이 충돌할 수 있었다.

코딩 에이전트는 이런 차이를 보기 좋은 부하다. 같은 시스템 프롬프트와 도구 정의를 반복해서 보내고, 같은 대화 뒤에 결과를 덧붙여 요청한다. 이전 입력과 겹치는 앞부분이 길 수 있다.

다만 “비슷한 작업”이라는 이유만으로 캐시가 맞는 것은 아니다. 같은 오류를 수정하더라도 입력 코드나 순서가 다르면 prefix가 달라진다. 재사용할 수 있는 것은 실제 토큰이 일치하는 앞부분이다.

DP에서도 같은 대화나 prefix를 가진 요청을 같은 엔진으로 보내면 캐시를 활용할 수 있다. 반대로 한 엔진에 지나치게 몰아 보내면 대기 시간이 길어진다. 캐시 적중률만 높이는 것으로 운영 구성을 결정할 수는 없었다.

## 지금은 TP 8과 EP 그리고 EPLB를 쓰고 있다

현재 실측에서는 TP 8, DP 1, EP와 EPLB를 함께 사용하는 구성이 가장 빠르게 느껴졌다. 그래서 지금은 이 구성을 기준으로 운영하고 있다.

이 조합을 “모든 레이어를 TP로 나눈다”고 이해하면 실제 동작과 다르다. EP가 활성화된 Expert 계층은 Expert 단위로 분산되고, Attention은 TP 8을 사용한다. 여기서 EP 크기는 TP × DP이므로 8이다.

| 구성 요소 | 현재 맡는 역할 |
| --- | --- |
| TP 8 | Attention 계산을 GPU 8장에 분산 |
| DP 1 | 요청을 한 엔진에서 스케줄링 |
| EP 8 | Expert를 GPU 8장에 분산 |
| EPLB | Expert 사용량에 따라 배치를 재조정 |

DP 1에서는 여러 DP 엔진에 캐시가 흩어지는 문제를 피할 수 있다. 요청이 한 엔진에 모이므로, 그 안에서 배치를 구성할 수도 있다. 이 특성이 현재 부하에 잘 맞았을 가능성이 있다.

그렇다고 속도 차이를 전부 캐시로 설명할 수는 없다. TP 크기에 따른 Attention 연산과 통신 비용, 배치 크기, 사용 커널도 함께 달라진다. 캐시가 주로 입력 재처리를 줄이는 반면, 출력 생성 속도에는 다른 요인도 작용한다.

EPLB는 이 중 Expert 쪽을 다루는 기능이다. MoE가 토큰마다 일부 Expert만 사용하더라도 일이 GPU마다 균등하게 나뉜다는 보장은 없다. 한 GPU에 일이 몰리면 다른 GPU가 기다릴 수 있다. EPLB는 실제 사용 통계를 보고 Expert 배치를 조정해 이런 편중을 줄인다.

코딩 요청이 많으니 특정 Expert에 몰릴 것이라는 생각도 해 봤다. 하지만 그것은 라우팅 통계로 확인해야 하는 가설이다. 현재 조합이 빠르다는 관찰과, 어떤 Expert가 왜 바빴는지를 밝혔다는 주장은 구분해 두려고 한다.

## 병렬화 밖에도 조정할 값이 많았다

현재 저장소에 기록한 설정에는 prefix caching, chunked prefill, MTP도 들어 있다. 이 옵션들은 같은 일을 하는 가속 스위치가 아니다.

| 현재 설정 | 다루는 부분 |
| --- | --- |
| Prefix caching 활성화 | 반복되는 입력 prefix의 계산 재사용 |
| Chunked prefill 활성화 | 긴 입력을 나눠 스케줄링 |
| 배치 토큰 상한 8192 | 한 스케줄링 단계에서 처리할 토큰 예산 |
| 최대 시퀀스 64 | 엔진이 동시에 처리할 시퀀스 상한 |
| MTP 5 | 여러 후보 토큰을 예측하고 검증하는 생성 경로 |
| 비동기 EPLB | Expert 부하 재조정 |

배치 토큰 상한 8192는 입력을 8192토큰까지만 받겠다는 뜻이 아니다. 최대 컨텍스트는 따로 정하고, 긴 입력은 여러 단계에 걸쳐 처리한다. 이 둘을 구분하지 않으면 긴 코드를 받아야 하니 배치 토큰도 무조건 크게 잡아야 한다고 생각하기 쉽다.

MTP도 후보 토큰 수를 크게 잡는다고 그만큼 빨라지는 것은 아니다. 예측과 검증에 비용이 들고, 예측한 토큰이 얼마나 채택되는지에 따라 이득이 달라진다. 과거 기록에는 1개와 3개를 사용한 시점도 있고, 현재 설정은 5개다.

KV 캐시 dtype으로는 현재 운영 명령에 `fp8_ds_mla`가 들어 있다. 이 역시 모델 가중치의 양자화와는 구분해야 한다. 모델·GPU·vLLM 구현 조합에 따라 지원 범위가 달라지므로, 다른 환경에 그대로 옮길 때는 별도로 확인해야 한다.

이 설정들을 소개하는 이유는 그대로 복사하면 최적이 된다는 뜻이 아니다. 어떤 값을 바꿨을 때 입력 처리, 생성, 메모리, 동시성 중 어디가 달라지는지 구분할 필요가 있었기 때문이다.

## 느린 구간을 나누어 봐야 다음 변경을 정할 수 있었다

이전 글에서 다뤘던 스트리밍 문제도 같은 맥락이었다. 모델이 응답을 보내고 있는데 게이트웨이가 4KB를 모아 읽느라 사용자에게 늦게 전달한 적이 있었다. GPU 설정만 바꿨다면 해결하지 못했을 문제다.

지금은 “느리다”는 말을 들으면 먼저 어느 구간인지 나눠 보려고 한다.

| 관찰한 현상 | 먼저 확인할 부분 |
| --- | --- |
| 요청한 뒤 첫 출력까지 오래 걸림 | 대기열, 입력 길이, 캐시 적중, prefill, 전달 지연 |
| 출력은 시작했지만 토큰 사이 간격이 큼 | decode, 배치 부하, 통신, Expert 편중 |
| 서버는 출력하는데 화면에서는 몰아서 보임 | 게이트웨이와 클라이언트의 스트리밍 |
| 특정 사용자·클라이언트에서만 실패 | 요청 형식, 도구 스키마, 응답 해석 |

최종 설정과 함께 남겨야 하는 것도 늘었다. 모델과 빌드 버전, 입력·출력 길이, 동시 요청 수, 캐시가 비어 있었는지까지 알아야 다른 실행의 결과를 비교할 수 있었다.

현재 TP 8·DP 1·EP·EPLB 조합이 잘 맞는다는 판단도 이 서비스의 부하 안에서 내린 것이다. 사용자가 늘거나, 긴 입력이 더 많아지거나, GPU와 추론 엔진이 바뀌면 다시 비교할 수 있다.

당장은 이 구성을 유지하면서 피크 시간의 첫 토큰 지연과 사용자별 생성 속도를 더 보려고 한다. 예전에는 컨테이너가 종료되지 않는지를 먼저 봤다면, 이제는 여러 사람이 작업을 이어갈 때 누가 어디서 기다리는지를 보는 쪽으로 관심이 옮겨 왔다.

실행 명령은 지금도 바뀔 수 있다. 다음에 다시 바꿀 때에는 이전 값으로 되돌아간 이유까지 알아볼 수 있도록 기록을 남기고 있다.
